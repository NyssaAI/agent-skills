# Learn from approved corrections

Learning requires a request to refine the profile or explicit approval of the proposed profile change. Ordinary revision and approval of a finished draft do not authorize profile writes. A direct instruction such as “remember that I prefer short openings in emails” authorizes that specific update.

Compare the prior draft and the accepted correction, then separate:

| Change | Treatment |
| --- | --- |
| Sentence rhythm, diction, contractions, warmth, opening or closing | Candidate voice rule, scoped to the relevant context |
| Formatting, citation requirements, publication structure | Candidate style standard with its destination scope |
| Dates, names, amounts, evidence, commitments, intent, uncertainty | Factual correction; do not generalize into voice |
| One-off task constraint or quoted third-party language | Keep task-local unless the user explicitly requests a reusable rule |

For example, changing “I will deliver Friday” to “I may deliver Monday” changes commitment, uncertainty, and timing; it is not evidence that the user likes tentative language. Changing “Please be advised” to “Here's the update” may support a plain opening preference when the user authorizes learning from it.

Propose the smallest useful rule that explains an accepted style correction. Identify the source and scope; do not turn one correction into a universal prohibition. Check existing explicit preferences and modes before appending duplicate or contradictory rules. If the user directly specifies the desired rule, apply it as requested. Resolve conflicts with existing guidance according to the user's instruction; propose uncertain interpretations before persistence.

Use [storage](storage.md) to preserve recoverable history, apply the authorized update, and read it back. Report the specific learned rule and distinguish any unresolved hypothesis. Retain the corrected draft as an example only when the user has approved retaining it.
