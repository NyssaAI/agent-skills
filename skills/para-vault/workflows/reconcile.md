# Workflow: Reconcile Vault Documents

> [!IMPORTANT] Scope Directive
> This workflow handles reconciling overlapping or conflicting prose notes in `vault_root`, proposing substantive revisions, and applying approved revisions while preserving document history, canonical authority, and `daily-tasks` structured work records (`RecordKind`). It does NOT own filing new captures (owned by `file.md`), general file operations (owned by `manage-file-operations`), or archiving completed projects (owned by `archive.md`).

Revise or reconcile the named documents in `vault_root` within the requested purpose and approval scope.

1. Read [shared vault conventions](../references/vault-conventions.md) to locate applicable governing rules. Inspect the documents, evidence, and existing approval history. Read the relevant [metadata and authority rules](../references/frontmatter-schemas.md), including `RecordKind` work-record rules and legacy compatibility before interpreting `document-maturity` or `state`. A workflow update does not authorize metadata migration.
2. **Preserve `daily-tasks` Work Records Intact**: When inspecting `1-projects/` (`project-index.md`, `mN-<slug>/<slug>.md`, `tN-<slug>.md`, `blockers/bN-<slug>.md`) or `2-areas/daily-plans/YYYY.MM.DD-daily-plan.md`, recognize valid `daily-tasks` work records (`RecordKind`: `project`, `milestone`, `task`, `blocker`, `daily-plan`) governed by `state` (`ProjectState`, `MilestoneState`, `TaskState`, `BlockerState`). **Never** rewrite valid `daily-tasks` work records into generic prose notes, strip `## Definition of Done` checklists (`<!-- id: UUID -->`) or `<!-- ref: UUID -->` links, inject `document-maturity` where not required, or write the retired `task-state` field.
3. Follow [reconciliation and protected revisions](../references/revisions.md) for prose knowledge and resource notes (`2-areas/` non-plan notes, `3-resources/`). Distinguish duplicates from independently authored notes; preserve unique content and provenance, identify contradictory claims, and separate supported resolutions from unresolved claims. Canonical precedence (`canonical: true`) selects the governing document without automatically disproving every other claim.
4. For substantive changes to `established` notes, create the specified proposal unless the user has already approved that specific revision. Keep the accepted original and current links while approval is pending. Complete independent work and report only conflicts that block the requested result.
5. Apply approved changes using the protected-revision procedure: preserve durable accepted history, retain identity for the same purpose, and change `canonical` authority only as authorized. When migrating legacy metadata with explicit user authorization, preserve operational `state` and never emit retired `task-state`. For unchanged archive snapshots, use [companion metadata](../references/lifecycle.md#archive-workflow). Use [manage-file-operations](../../manage-file-operations/SKILL.md) when copies or moves are needed.
6. Check the result against the approved changes and preserved evidence. Update [relevant navigation](../references/navigation.md#index-ownership-and-links), mark applied proposals accurately, and report document paths, recovery history, acceptance/canonical state, and unresolved claims.

Minor corrections and routine link maintenance can be applied directly with the recoverability required by the revision guidance (`vault_root/.temp/`, never `.nyssa-ai/`). Read the schema directly for metadata-only questions; consulting it does not require starting a revision workflow.
